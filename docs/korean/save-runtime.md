# DOS 저장·복원 합성 검증

현재 승인 빌드는 [EXTRA+SAVE](extra-save.md)를 사용한다. 아래 별도 저장 디스크 설명은 이전 합성 검증 당시의 구성이다. 원시 저장 위치와 형식은 동일하다.

추가 DOS 디스크의 콜드 부팅에 저장/복원 연결을 추가했다. 실제 한국어 번역은
사용하지 않으며 원래 영문 대사와 합성 한글 제목으로 실행한다.
[검증 증거](../evidence/korean/save-probe.json)는 시작 경로의 동일 세션 복원,
새 부팅 복원, 호환되지 않는 저장 및 중간 I/O 실패 복구를 검사한다.

## 저장 형식과 코드 배치

원래 스냅샷은 그대로 main RAM `$2000–$AFFF`의 144페이지를 저장 디스크
T23/S0–T31/S15에 기록한다. LC와 `$2000` 미만 intrinsic 코드는 저장하지 않는다.
한국어 후보 형식은 **T22/S15 한 섹터를 추가 예약**한다. 이는 별도 저장 디스크의
원시 영역이며 일반 DOS 파일을 함께 저장하는 용도로 사용하지 않는다.

- 헤더의 처음 16바이트는 `KOS1`과 빌드 식별값 12바이트다. 나머지는 0이다.
- 빌드 식별값은 런타임, 부트 코드, 글꼴, 상주 풀, 소스 파일, 패키지 및
  재빌드한 영문 A/B 이미지의 바이트에서 결정한다.
  다른 빌드와 원판 저장은 지원하지 않고 읽기 전에 거부한다.
- 저장 시작 전에 헤더를 0으로 지운다. 모든 스냅샷 쓰기 성공 후에만 식별값을
  기록한다. 중간 쓰기 실패 때 이전 식별값을 남겨 부분 저장을 유효하게 만들지 않는다.
- 기존 영문 소스 빌드는 조건부 코드를 사용하지 않으며 A/B 해시는 그대로다.

`src/intrinsics.s`의 `KOREAN` 연결은 기존 save/restore 진입점의 크기를 유지한다.
원래 사용하지 않던 `$1F6E–$1FFF`의 146바이트에 `restore-guard.inc`를 넣었다.
식별값은 `$1FF0`에 고정하고 링커/빌드에서 검사한다.
main 확장 코드는 `$9400–$9B19` 1,818바이트이며 2KB 예약 영역에 230바이트가 남는다.

## 부분 복원 실패의 처리

복원 전에 `$0700` 버퍼로 T22/S15를 읽고 현재 빌드의 식별값과 비교한다.
불일치나 읽기 오류는 월드·스크립트·확장 코드를 덮어쓰기 전에 거부한다.
그다음 원래 intrinsic 루프가 144페이지 전체를 읽는다.

읽기 도중 오류가 나면 부분 월드로 반환하지 않는다. `$1F6E` 영역의 복구 코드가
저장한 스택 깊이로 돌아가 원래 ASCII 프린터 `$0BF3`와 스냅샷 밖의 HGR 렌더러로
`RESTORE ERROR. RETRY: RETURN`을 출력한다. Return은 헤더 검사부터 전체 복원을
다시 시작한다. 손상됐을 수 있는 `$9400` 런타임이나 방/라이브러리 메시지를 호출하지 않는다.

이 영문 안내는 복구 경로 실험용 기술 문구다. 최종 제외/번역 정책과 사용자 안내는
검수 패키지에 명시해야 한다. 중간 복원 오류에서 재시도 없이 게임으로 돌아가는
취소 경로는 제공하지 않는다.

## LC 캐시 재적재

완전한 스냅샷 복원 뒤에만 확장 런타임으로 진입한다. 스냅샷에서 복구한 마지막
방 패키지 이름으로 해당 게임 디스크를 요청하고 LC 방 풀을 무효화/재적재한다.
`ko_load_pool`은 KOR2 헤더와 스크립트 EOF를 검사하면서 스크립트 본문을 소비하되
main RAM에는 쓰지 않는다. 저장된 스크립트의 매크로 수정 상태를 보존하기 위해서다.
새 풀을 완전히 읽은 뒤에만 크기를 공개한다.

글꼴·상주 풀은 새 부팅 때 초기화한 자료를 사용한다. 같은 빌드 저장만 허용하므로
메시지/글리프 ID가 일치하며, 저장 디스크가 삽입된 동안에도 상주 문구를 출력한다.
현재 후보는 새 미디어 요청 뒤 원래 `!CONT` 안내가 한 번 더 나온다.
최종 UI에서는 이 중복을 제거하고 요청 면/빌드 식별을 통합해야 한다.

## 검사 범위

```sh
python3 tools/build.py --output build/korean/english-baseline
python3 tools/korean/verify_save.py \
  --rompath /path/to/roms --output build/korean/save-validation-new
```

검증기는 복사된 시작/게임/저장 이미지와 소유 MAME 프로세스를 사용한다.
정상 동작은 콜드 부팅과 키 입력만으로 진행한다. 실패 프로필은 명시적으로
RWTS IOB의 요구 volume을 한 요청 동안 1로 지정하여 실제 volume 254 매체에서
native RWTS가 `$20` 오류를 반환하게 한다. 오류 뒤 원래 volume 설정을 복구한다.

1. 방 3에서 저장하고 `SE`로 방 2에 간 뒤 같은 세션에서 복원한다.
   방 3, 다섯 객체 배열, 118바이트 방 풀 및 저장된 방 스크립트를 대조한다.
2. 새 부팅한 방 1에서 잘못된 식별값을 가진 저장을 거부한다. 월드/방 풀을
   보존하고 올바른 저장으로 교체한 뒤 방 3으로 복원한다.
3. 다른 새 부팅에서는 저장 복사본의 `$9400–$9BFF` 페이지를 `$CC`로 채운다.
   그 페이지들이 실제 적재된 다음 `$9300` 페이지 요청에 읽기 오류를 주입한다.
   복구 안내 중 확장 코드가 손상됐음을 확인하고, 올바른 저장으로 교체해
   144페이지 전체를 재시도한다. 이 구간에 확장 코드 실행이 없었는지 추적한다.
4. 저장 중 `$9300` 페이지에 쓰기 오류를 주입한다. 유효 헤더를 발행하지 않았고
   그 저장의 복원을 스냅샷 첫 페이지 전에 거부하는지 확인한다.

유효 저장은 헤더 무효화·144페이지·헤더 커밋의 146개 쓰기 요청이다.
바이트 변경 범위는 T22/S15와 원래 144섹터 안으로 제한된다. 모두 0인 RAM 페이지를
이미 0인 섹터에 쓰면 바이트 차이는 없으므로 요청 추적과 내용 검사를 함께 사용한다.
LC 글꼴과 상주 풀을 각 프롬프트에서 기대값과 비교한다.
[부분 복원 실패 안내 화면](../evidence/korean/restore-retry.png)도 확인했다.

## 남은 검증

이 결과로 전체 K5/K6가 완료되지는 않는다. B면 저장/새 부팅 복원은
[전체 합성 실행](full-media-runtime.md)에서 별도로 통과했다. 승인 번역의 최종 전체 디스크
세트, 게임 매체의 면/버전 식별, 중복 없는 승인된 UI, 재시작, 시간 제한 장면과
엔딩 회귀가 남아 있다. 헤더는 빌드 일치와 쓰기 완료를 검사하며 스냅샷 전체의
내용 체크섬은 아니다. 물리 섹터의 읽기 검사는 native RWTS에 의존한다.
실제 Apple II+ 하드웨어 검증과 사람의 번역 승인은 별도다.
