# 합성 메시지 런타임 검증

`src/korean/messages.s`는 후보 인코딩을 읽는 6502 코드다. `lc.s`와 함께 main RAM
`$9400`에 연결하며 LC/메시지/래퍼 부분은 793바이트다. [스트리밍 로더](loader-runtime.md)를
포함한 현재 통합 바이너리는 1,818바이트이며(dispatcher 포함) 2KB 링커 영역에 230바이트가 남는다.
저장 복구 guard는 이 영역 밖의 `$1F6E–$1FFF`를 사용한다. 전체 게임/최종 UI까지
공간이 충분한지는 최종 통합에서 다시 검사한다.

## 인터페이스

`ko_print_message`: A/X에 16비트 메시지 ID의 low/high 바이트를 전달한다. bit15가
설정되어 있으면 bank1의 상주 풀, 아니면 bank2의 현재 파일 풀을 사용한다.
성공 시 C=1, 잘못된 ID·풀 크기·오프셋·제어 토큰·글리프나 잘린 스트림이면 C=0이다.
호출 전에 decimal mode가 clear여야 하며 재진입은 허용하지 않는다.

로더는 완전한 적재/검증 이후에만 `ko_room_size`, `ko_resident_size`, `ko_font_count`를
설정한다. 아직 로드하지 않았거나 복원으로 캐시가 무효화된 경우 해당 크기는 0이다.
현재 허용 범위는 방별 풀 1KB, 상주 풀 4KB, 공통 영역 글꼴 1,024개(8KB)다.
시작 단계에서 `lc_detect`를 통과한 뒤 사용해야 한다.

메시지와 글리프를 읽을 때 잠시 IRQ를 막고 LC를 선택한 뒤, main RAM으로 가져온다.
ROM 호출 전에 `$C082`로 ROM을 복구하고 LC 쓰기를 비활성화한다. 호출자의 IRQ
상태는 복구한다. 문자마다 매핑을 바꾸므로 성능은 실제 시간 제한 장면에서 따로
측정해야 한다. NMI 처리나 실제 주변 장치 인터럽트까지 검증한 것은 아니다.

ASCII는 ROM COUT → 원본 HGR 렌더러를 사용한다. 한글은 8바이트 임시 글리프를
원본 scanline 루틴으로 그린 뒤 원본 커서 전진 루틴을 호출한다. 두 HGR 페이지,
역상, 40열 줄바꿈, 15행 클램프를 그대로 따른다. 스크립트의 마지막 CR은 이 API가
자동으로 추가하지 않는다. 내부 LF는 원본 CR 출력으로 처리한다.

`ko_print_script_string`: 원본 문자열 출력 함수와 같은 A/X 문자열 포인터를 받는다.
`~hhhh` 뒤에 원래 CR 또는 `;`+CR이 있는 경우만 메시지 참조로 해석한다.
네 자리 high-bit 대문자 16진수를 읽고 메시지를 출력하며 세미콜론이 없으면 원래처럼
줄바꿈한다. 다른 문자열은 원본 `print_script_string`을 호출한다. 잘못된 참조는
C=0이며 출력하지 않는다(이미 출력 중에 본문 오류가 나면 일부 출력은 남을 수 있다).

직접 메시지 함수는 인터프리터 ZP를 변경하지 않는다. 스크립트 래퍼는 원본 프린터처럼
`$E7/$E8`을 사용한다. A/X/Y, flags 및 기존 렌더러 작업 영역은 보존 대상이 아니다.
본문 파싱 상태는 별도 main RAM 변수에 보관하므로 COUT가 글리프 포인터를 바꿔도
메시지 읽기를 계속할 수 있다.

## 검증

```sh
python3 tools/korean/build_messages.py
python3 tools/korean/verify_messages.py \
  --rompath /path/to/roms --output build/korean/message-validation-new
```

검증기는 새 출력 디렉터리와 복사된 영문 디스크를 사용하는 소유 MAME 프로세스를
실행한다. debugger 명령 경계에서 테스트 코드, 영문 소스 빌드의 렌더러와
`KOREAN=1`로 조립한 인터프리터를 적재한다. 합성 자료는 실제 번역 카탈로그를
읽지 않는다. CPU가 테스트 버퍼의
폰트·풀을 LC로 복사한 뒤 시험을 수행한다. 이는 디스크 로더 시험이 아니다.

[채택된 증거](../evidence/korean/message-probe.json)는 Apple II+ 48K + slot0 Language Card에서:

- 46개 성공/실패 시나리오와 커서 결과를 확인했다.
- 두 HGR 페이지 전체 16,384바이트를 호스트에서 독립적으로 그린 기대값과 비교했다.
- 4KB 상주 풀, 1KB 방별 풀, 8KB 글꼴 총 13,312바이트가 변하지 않았음을 확인했다.
- 두 LC 뱅크, 메시지의 페이지 경계, 마지막 풀 바이트의 종료자, 글리프 ID의
  low byte가 제어값인 경우 및 마지막 글리프의 `$FFFF` 접근을 검사했다.
- 잘못된 ID/크기/오프셋/헤더/제어 코드/글리프, 잘린 글리프, 없는 종료자를 거부했다.
- 참조 문자열의 CR/세미콜론, 숫자·`OK>^` 원본 출력 및 잘못된 참조 문법을 검사했다.
- 네 native 오류 진입점(`file_not_found`, `disk_error`, `input_without_cr`,
  `script_stack_overflow`)을 두 HGR 페이지에서 직접 호출했다. 방 풀이 무효인
  상태에서도 상주 한글 참조와 기존 ASCII가 출력되고 원래 두 추가 CR이 유지된다.
  각 오류의 실제 발생 조건을 재현한 시험은 아니며, 합성 PARMS 문자열을 사용했다.
- 각 호출 후 ROM WAIT로 돌아왔으며, IRQ mask 보존과 주요 인터프리터/상태 영역의
  표식 보존을 검사했다. debugger가 LC를 다시 살펴보기 전에 ROM 매핑을 확인했다.

[화면](../evidence/korean/message-probe.png)은 합성 문자열과 경계 검사 문자다.
아티팩트 색이 포함된 native HGR 화면이다. 읽기 좋은 최종 게임 화면이나 번역 검수
미리보기로 취급하지 않는다.

`print_engine_error`는 한국어 빌드에서 `ko_print_script_string`을 호출한다.
기존 직접 ASCII 호출로 빠지던 경로를 연결했으며 명령어 길이와 모든 오류 진입점의
주소는 유지했다. 복원 실패 guard의 `$0BF3` 호출은 확장 코드가 부분 복원으로
손상될 수 있으므로 ASCII로 유지한다. [영문 재빌드 검사](../evidence/korean/english-error-regression.json)는
기본 interpreter 바이너리와 A/B 디스크가 기존 기준선과 바이트 단위로 같음을 확인했다.

## 남은 통합

원본 LIBRARY를 참조화하면 `$93A4`까지 사용하므로 `$9400` 코드가 들어갈 후보 공간이
생긴다. [합성 콜드 부팅](startup-runtime.md)에서 시작 경로의 공존을 확인했다. 원본 영문
LIBRARY에 이 코드를 그대로 겹쳐 적재해서는 안 된다.

KOR2 파일의 합성 스트리밍 적재와 추가 디스크 콜드 부팅·초기 방 전환·잘못된 영문
디스크 재시도는 검증을 통과했다. [새 부팅 복원](save-runtime.md)도 시작 경로에서 통과했다. [전체 합성 실행](full-media-runtime.md)은 B면 복원과 전체 자원 적재도 통과했다. 승인 번역의 통합은 남아 있다. `$9400`은 저장 스냅샷 범위에 있으므로 복원 중 실패
처리는 별도 영역에서 수행해야 한다. 화면 조합과 시간 제한 장면의 게임 수준 검증도
남아 있다. 번역 적용과 사람 승인은 이 합성 검사와 별개다.
